# 2026-08-19 本地审计历史清除反思

## 背景

Activity 页面既要让用户理解近期本地调用，也要提供不可恢复的历史清除入口。难点不在 DELETE 本身，
而在把“用户可见的审计投影”与防重放、timer、设置、identity、credential 及服务端审计明确分开。

## 稳定经验

### 1. 可清展示历史不能清执行真相

`commands` 保存同一 `commandId` 的终态，是防止副作用重放的安全状态；`audit_records` 只是解释近期
本地调用的元数据。若把两者合并清除，用户清历史会意外恢复旧命令的执行资格。契约应直接证明
“执行一次 -> clear audit -> replay 同 id”，handler 仍只执行一次，新审计只记录 `replayed`。

### 2. destructive confirmation 必须描述集合而非抽象承诺

“清除历史”容易被理解成完整数据删除。确认页同时列出实际删除对象和明确保留对象，才能避免把它
误读为取消命令、清 timer、重置设置/identity/credential、网关撤销或服务端审计清除。

### 3. 删除完成不等于页面可以发布任意旧快照

异步 refresh 可能在 DELETE 前读到旧列表、却在 DELETE 后才发布。用单调 audit revision 让 clear 前
启动的 refresh 失效，比依赖完成顺序可靠；DELETE 线性化后新增的审计则应继续保留，不能被“清空 UI”
的本地状态覆盖。

### 4. 失败和空集合都需要数据库真实结果

清除失败时不移除当前展示、不显示成功；fresh install 清除返回真实 0 条，也不伪造有数据被删除。
这让 UI 文案描述数据库已确认的事实，而不是按钮点击意图。

## 后续复用检查

- 新增清除入口时，先列出删除集合、保留集合、外部系统和正在进行的副作用。
- 审查 retention 时同时覆盖启动 prune 与每次写入硬上限，避免只在重启时才恢复边界。
- 对“清除后不可重放”使用有副作用 command 的端到端本地 contract，不只断言 SQL 文本。
- emulator 空历史 smoke 只证明确认交互与真实 0 条结果；有记录、并发写入和服务端清除必须分别取证。
