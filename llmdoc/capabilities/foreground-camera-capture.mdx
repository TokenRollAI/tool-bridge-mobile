# 仅前台相机拍摄参考

## 能力契约

公开能力是 `phone/camera.capture_photo`。descriptor 固定为 `effect: write`、`risk: high`、
`confirmation: always`、`queuePolicy: reject_offline`，每个 caller/全局每 60 秒最多 2/4 次，inline result
最多 4 KiB。

strict input 只有：

- `purpose`：trim 后 1–120 个字符，拒绝 control 与 bidi override/isolate；
- `facing: front | back`，默认 `back`；
- `quality: low | medium | high`，默认 `medium`。

strict result 只有稳定 `store://default/[A-Za-z0-9_-]{22,64}` `objectRef`、`mimeType: image/jpeg`、bytes、
width、height 和照片字节 SHA-256。照片内容、Store capability、relay URL、App 私有 `file://` URI和对象
`expiresAt` 都不能进入结果。

## 前台、权限与 UI 状态

controller 在入口要求 React Native `AppState === active`，同一时刻只允许一个拍摄流程。原生硬件 probe
复用 `ToolBridgeAttention.getAvailableCameraFacingsAsync()`：Android 通过 Camera2
`CameraManager.cameraIdList` + `CameraCharacteristics.LENS_FACING` 枚举，iOS 通过 AVFoundation
`AVCaptureDevice.default(.builtInWideAngleCamera, for: .video, position:)` 分别检查前/后镜头。它只返回
schema 支持的 `back | front`，不创建 `AVCaptureSession`、不打开采集流、不读取照片；Web 返回空数组并
fail closed。`CameraView` 只负责后续可见预览和拍照，`CameraView.isAvailableAsync()` 是 Web-only API，
不能作为 Android/iOS 原生硬件 probe。

执行顺序固定为：strict 参数通过后，argument-aware preflight 先要求当前调用的 Store upload service，再
枚举镜头；缺服务时以 `camera_upload_unavailable`、requested facing 不存在时以
`camera_facing_unavailable` 拒绝，两者都不可重试，且发生在 admission、通用 probe 和本地确认之前。因此
老 Gateway 或过期 upload capability 不会先弹确认、打开相机或产生照片。随后通用 probe 先检查前台，再
要求枚举结果至少有一个 `back | front`，最后才读取当前系统 Camera 权限。native 枚举异常、未知 facing
或权限读取异常稳定映射为 `camera_probe_failed`，不把原始异常详情返回远端；空枚举映射为
`camera_unavailable`。权限可再次请求映射为 `permission_required`，永久拒绝映射为 unavailable。远程
handler 与 probe/preflight 都不请求权限；权限只能由全屏相机流程或设置页的本地用户操作触发。

`ApplicationRuntime.handleAppStateChange()` 一旦离开 `active` 就同步调用
`cancelForForegroundLoss()`。controller 在取得照片、处理后和上传后也复检 foreground、取消和 deadline；
因此等待权限/预览、拍摄和重编码期间切后台会终止本地流程，上传返回后也不会提交成功结果。已知限制是
当前 SDK 0.21.0 的 call-scoped `uploadObject` 仍不接受 controller 的额外 AbortSignal：如果 Store HTTP 上传已经
开始，前台丢失不能保证终止该网络副作用，不能把本地失败结果表述为“对象一定未上传”。

descriptor 的 `confirmation: always` 不因 Direct call 改写。具体 UI 分支由本机 control mode 决定：

- Ask every time / Trusted session：先经过通用本地确认；全屏可见预览中由用户按快门，随后可重拍或
  “使用并上传”。
- Direct call：本机全局策略跳过逐次确认；仍挂载全屏可见 `CameraView`，展示 caller、purpose、自动拍摄
  提示和取消入口。`onCameraReady` 后延迟 300 ms 自动调用拍照，不提供用户快门，也不进入拍后复核。

两条路径都设置 `exif: false`、`shutterSound: true`。系统相机指示、快门声和平台焦点顺序属于真机行为，
不能由组件测试或配置推断。

## 图像处理与临时文件

系统产出的原始私有文件最大 30 MiB。处理层总是重编码 JPEG；low/medium/high 的最长边分别为
1280/1920/2560，压缩系数分别为 0.55/0.75/0.9。输出最大 10 MiB，并复核 JPEG SOI/EOI 后计算
SHA-256。已知的成功、失败、取消和重拍路径都对原始/处理文件 best-effort 删除，URI 不进入结果或日志。

当前没有 App 崩溃后扫描相机孤儿文件的契约，不能把 best-effort 清理写成 crash-safe 生命周期保证。
照片从不写入系统相册；相册中没有新照片是设计事实，不能作为“没有触发硬件拍照”的证据。

## 当前 SDK 0.21.0 Store 对象上传

移动端只消费 `@tool-bridge/sdk/device@0.21.0` 为当前 `DeviceCallHandler` 提供的 `call.uploadObject`；该
入口由 0.17 首次交付，0.21.0 继续提供。`expo/fetch` 作为 SDK connection fetcher 支撑 React Native Blob
上传：

```text
处理后的 JPEG Blob
  -> call.uploadObject(body/contentType/size/checksum/filename/idempotencyKey)
  -> SDK 内部 POST system/store/create_upload（x-tb-store-capability）
  -> SDK 内部 PUT relay upload URL（二进制 body）
  -> 严格核对稳定 StoreObjectDescriptor
  -> capability result
```

上传参数固定为：

- `contentType = image/jpeg`；
- `size =` 实际处理后字节数；
- `checksum = sha256:<照片 SHA-256>`；
- `filename = <sha256(commandId)>.jpg`；
- `idempotencyKey = camera-<sha256(commandId)>`。

uploader 只接受 `store://default/[A-Za-z0-9_-]{22,64}`，并核对返回 descriptor 的 JPEG MIME、真实 size
与可选 checksum；Store object id 由服务端分配，移动端不指定 context/entry path。Gateway 必须为本次
device call 下发尚未过期的 upload capability；该能力缺失时 transport 不下传 uploader。移动端确定性
filename/idempotency key、10 MiB 上限和 descriptor 核对是 consumer 约束，不代表服务端已完成
command/device/MIME/大小/TTL/checksum/single-use 的全部强绑定。

wire upload token 留在 SDK 内部；移动端 invocation services 只有窄 `uploadObject(options)`，不得持久化或
写日志。`call.uploadObject` 的公开 options 不含 caller-provided `signal`，SDK 内部只使用原始 call signal；
当前 controller 的前台 AbortController 因此不能组合进去。用 `Promise.race` 提前返回也不能终止内部 fetch。

相机 call 的本地 ceiling 是 120 秒，普通 realtime command 是 30 秒；有权威 Gateway `expiresAt` 时取
Gateway、本地 ceiling 与 upload capability expiry 的最早值。2026-08-26 历史现场 Gateway 0.17 的
device call authority 约为 60 秒，因此当时 120 秒本地 ceiling 不会延长真实调用；这不是当前 0.21.0
Gateway 回归证据。context 缺失的旧 Gateway 只有本地 ceiling，同时没有 Store upload service，相机会在
preflight fail closed。

## 验证边界

可声明的稳定实现事实：本地相机流程与当前 SDK 0.21.0 call-scoped Store consumer 已集成；专项自动化覆盖
schema、缺 upload capability 在确认/probe 前拒绝、两种 UI 分支、前台丢失的本地取消、图像/descriptor
边界，以及真实 SDK supervisor 的 `system/store/create_upload` + `x-tb-store-capability` + relay Blob
PUT。

2026-08-26 的 0.0.11 Preview APK 已在 Android 后置镜头 Direct call 下完成一次真实拍照、Store 上传、
stat 和受保护回读的 size/SHA-256 闭环；这只证明记录中的 artifact、设备、Gateway 和调用条件。iOS、其他
镜头/权限/生命周期矩阵、系统指示/快门声、上传中切后台，以及完整 U-7 服务端强绑定仍未验证。本地
自动化、prebuild 或单次真机成功不能替代这些层级。记录方法见
`llmdoc/delivery/verification-evidence.mdx`。
